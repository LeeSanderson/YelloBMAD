- (constraint) REVIEWER GATE FINDING (web-verification lens, verified, CRITICAL) — SUPERSEDES the single-statement-swap decision recorded earlier in this run. That decision rested on the claim that SQL Server evaluates a unique index at statement completion. THE CLAIM IS FALSE. Verified 2026-08-19: SQL Server has no deferred constraint enforcement at all — uniqueness is checked per row as the index is maintained, and SET CONSTRAINTS DEFERRED exists in PostgreSQL and Oracle but not in SQL Server (Microsoft Learn on UNIQUE constraints; corroborated across multiple sources describing the temporary-value workaround as mandatory on SQL Server). A single UPDATE with a CASE over both Membership rows can therefore transiently write a second Owner row and fail on the AD-5 filtered unique index, depending on row processing order. CORRECTED to two ordered UPDATE statements in one transaction: demote the current Owner to Admin FIRST, then promote the recipient. This is airtight for a reason specific to this index and worth recording: the index is FILTERED on Role = Owner, so demoting removes the row from the index entirely leaving ZERO matching rows, and zero never violates uniqueness — which is also why the usual swap-via-temporary-value workaround is unnecessary here. Reverse order fails. EF Core tracked-entity SaveChanges is forbidden for this change because it picks its own statement order. NOTE THE PATTERN: this is the second SQL-Server-specific claim in this spine that was plausible and wrong, after Guid.CreateVersion7 in the original run. Both were caught by the same configured lens. Recommendation logged: treat any assertion about SQL Server engine behaviour in this project as unverified until checked against Microsoft documentation.

- (decision) CHANGE 2 - AD-29 ADDED, closing the FR-28 x NFR-5 x NFR-9 three-way deferral in which the PRD handed Board rendering to the architecture, no AD ever chose a mechanism, and the UX spine deferred back. DECISION: Board columns and List View pages are read by KEYSET (seek) pagination on the AD-15 position key, never OFFSET, and rendered rows are APPENDED to the DOM and never recycled. Why keyset: AD-15 already provides a sortable key unique within (ProjectId, StatusId), so a page is an index seek of bounded cost whose latency is independent of depth in the column, whereas OFFSET degrades linearly and would blow NFR-5 300ms p95 at the 5000-Task bound on 0.5 vCore with MAXDOP=1 - a budget that holds only near the top of a column is not a budget. Why NOT DOM virtualisation, the conventional answer, now forbidden: a virtualiser recycles row elements and a recycled row silently re-points keyboard focus at a different Task, so the next keyboard move operates on the wrong Task - a data-corrupting defect reachable only by keyboard, invisible to pointer testing, hitting precisely the users NFR-9 exists to protect. Appending makes it impossible rather than mitigated. The column count is a separate indexed COUNT carrying the TRUE total so aria-setsize and the visible chip agree. One mechanism serves both views, which FR-30 requires on the same terms as FR-28, and which the UX spine had independently chosen for the List View for the same focus-identity reason.
- (constraint) GATE - WEB-VERIFICATION LENS, VERIFIED, HIGH. AD-15 said the position key is lexicographically sortable and said nothing about collation. Lexicographic sortability is a property of the ALGORITHM; whether the database reproduces that order is a property of the COLLATION, and the two do not agree by default. Verified 2026-08-20 against Microsoft Learn: the Azure SQL Database default is SQL_Latin1_General_CP1_CI_AS - CASE-INSENSITIVE - under which a mixed-case fractional-index alphabet (base62 is the usual choice) makes a0 and A0 compare EQUAL, so ORDER BY is non-deterministic between them and the uniqueness constraint rejects the second as a duplicate. Also verified: ALTER DATABASE COLLATE is NOT supported on Azure SQL Database, so this cannot be retrofitted at server level and must be set at column definition. AD-15 amended: the key column and the (ProjectId, StatusId, PositionKey) index are declared COLLATE Latin1_General_100_BIN2 so comparison is by code point, which is what the algorithm assumes, and the migration enforces it.
