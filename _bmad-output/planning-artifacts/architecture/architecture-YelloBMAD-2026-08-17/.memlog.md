- (direction) Inputs: prd-YelloBMAD-2026-08-15/prd.md (status final) + addendum.md; docs/bmad-coverage.md as standing project context. Greenfield — no source code exists, stack fully open. No SPEC.md, no UX spec.
- (direction) Working mode: Coaching path. Deliverables agreed up front: (1) the spine as build substrate, (2) a human-readable rendering to review the design by, (3) an interactive HTML+SVG walkthrough deck to pressure-test and drive discussion.
- (constraint) PRD NFR-1: isolation absolute, the one requirement with no acceptable failure rate — a single verified cross-Space disclosure blocks release. Holds across browser, API, reads, writes, listings, aggregates, notifications and error messages, and for identifiers (holding an id confers nothing).
- (constraint) PRD FR-15/FR-9: authorisation is a function of (Account, Space), never Account alone. Active Space must be resolved BEFORE any authorisation decision; a request with no resolvable Space context is refused rather than defaulted. Cross-Space request must be indistinguishable from not-found; within-Space role failure must report permission-denied.
- (constraint) PRD FR-34 (PM-declared acceptance criterion the product is judged on): a Role change or Membership removal takes effect on open collaborative editing sessions within 5s (NFR-2) without the affected party acting; unsynchronised local changes are NOT applied; already-synchronised changes are retained. Addendum §4: the sync channel therefore cannot be a trusted path that authorises once at connection time.
- (constraint) PRD §6.3 cost ceiling: total running cost under GBP 30/month at NFR-8 scale. No design requiring always-on dedicated infrastructure per Space or per active editing session. Real-time (NFR-3/NFR-4) named as the most likely source of cost pressure and must be satisfied within a single modest deployment.
- (constraint) PRD NFR-3/NFR-4 real-time budgets: local edit renders <16ms with no network round trip; remote edit <300ms p95 at 50ms RTT; presence appears <2s and disappears <10s; participants converge within 2s; 10 simultaneous editors per Task; 5-minute disconnection reconciles without loss or duplication.
- (constraint) PRD addendum §3: a Project's Status delta must reference Statuses by IDENTITY, not by name — forced by FR-27 rename-cascade conflict detection. Statuses need stable ids surviving rename at both levels. Open: whether the effective set is derived per read or materialised and invalidated.
- (constraint) PRD NFR-8 scale envelope bounding the whole design: 50 Spaces/Account, 100 Memberships/Space, 50 Projects/Space, 5000 Tasks/Project, 10 concurrent editors/Task, 50 concurrent Sessions/Space. Exceeding a bound must degrade visibly (a refusal), never silently.
- (direction) USER: the solution will be built by BMAD dev agents story-by-story, not hand-built. Implication for the spine: invariants must be enforced by construction (type system, single choke point, lint/test gates) rather than by an agent remembering to read the spine. A rule that relies on discipline is not a rule here.
- (direction) USER: deployment is primarily LOCAL for testing; Azure is the stretch target, using cost-effective serverless compute that scales with usage so cost tracks usage. Implication: dev/prod parity matters (local must be a faithful stand-in), scale-to-zero is desirable, and no always-on premium service tier.
- (direction) USER: collaborative editing is to be OWNED by the architecture, not delegated to a hosted collaboration service (Liveblocks/PartyKit/Convex et al are out). Open sub-fork to resolve: whether 'owned' extends to hand-rolling the text-merge algorithm or stops at owning the sync protocol, authorisation seam, persistence and reconnection while using a proven CRDT library as a data-structure dependency.

- (constraint) FORCED BY COST — managed WebSocket brokers are out. Azure Web PubSub free tier caps at 20 concurrent connections and 20k msgs/day with max 1 unit; NFR-8 alone requires 50 concurrent Sessions per Space. Standard tier is ~USD 49/unit/month, which breaks the GBP 30 ceiling before any compute or database is bought. Azure SignalR Service has the same shape (free 20 connections, Standard ~USD 50). Conclusion: the WebSocket must terminate in our own compute, which is also what FR-34's per-message authorisation seam needs.
- (constraint) Verified 2026-08-17 — Azure Container Apps: HTTP ingress supports WebSocket, gRPC, HTTP/1.1 and HTTP/2 with TLS terminated at ingress. Consumption plan scales to zero with no usage charge at zero replicas. Free grant per subscription per month: 180,000 vCPU-s, 360,000 GiB-s, 2M requests; then ~USD 0.000024/vCPU-s and ~USD 0.000003/GiB-s. HARD CONSTRAINT: ingress request timeout is 240 seconds, so the sync protocol needs an application-level heartbeat comfortably under that or long-idle WebSockets are severed.
- (version) Verified 2026-08-17 — Azure cost components at NFR-8 scale: PostgreSQL Flexible Server Burstable B1ms ~USD 12/month on-demand (East US, compute only; storage/IOPS/backup extra). Azure SQL serverless with auto-pause only beats provisioned when the DB is idle >30-40% of the time. Azure Static Web Apps free tier: 100GB bandwidth, 1GB storage, 1 custom domain, free SSL — enough to host the client at zero cost.
- (question) Board ordering (FR-29) is a second, distinct convergence problem from text (FR-31) and is not solved by the same mechanism. Candidate: fractional indexing (Figma/Linear approach) with jitter to mitigate concurrent same-position interleaving; note that unjittered fractional indexing interleaves when two peers insert at the same slot. Research pointer: Fugue (arXiv 2305.00583) for maximal non-interleaving in text.
- (decision) USER CHOSE: own the sync layer (wire protocol, per-message authorisation, append-only update persistence, compaction, presence, reconnection); use a proven CRDT (Yjs/yrs family) as the text-merge primitive. Rejected: hand-rolling the merge algorithm (NFR-4's 10-editor convergence and 5-min offline reconciliation fail silently when hand-rolled, and dev agents building it story-by-story compounds that). Also rejected: fully opaque updates server-side, because FR-35 API reads and FR-30 List View need a trustworthy plain-text materialisation of Task descriptions.
- (decision) USER CHOSE: .NET 10 LTS (C#) as the server stack, over TypeScript end-to-end and over an explicit .NET+TS split. Accepted trade: the CRDT dependency is thinner on .NET (YDotNet 0.6.0, self-described early/API-unstable) than on JS. Consequence to bind as an AD: the CRDT library must sit behind one narrow port with exactly one adapter, so a version break or a swap to Ycs/direct yrs FFI is a local change rather than a system-wide one.
- (decision) USER CHOSE Blazor WebAssembly (C# everywhere) for the client, after being shown that YDotNet has no WASM native target and that the only Blazor+Yjs collaborative editors found are commercially licensed JS components. Concern was raised and the choice reaffirmed — treat as settled. Rejected: React+TS SPA with Yjs; Blazor Server (a stateful per-user SignalR circuit for the whole session collides with PRD 6.3's no-always-on-per-session rule and the GBP 30 ceiling).
- (decision) USER CHOSE Azure SQL Database serverless (auto-pause) over PostgreSQL Flexible Server. Rationale accepted: it matches the 'cost tracks usage' instruction most literally and is the natural EF Core pairing; row-level security is available via security predicates so the isolation floor is unaffected. Accepted costs: local dev/prod parity needs a SQL Server container rather than the same engine, and auto-pause resume adds cold-start latency to the first request after idle.
- (constraint) Blazor WASM forces a sub-decision on where the CRDT replica lives, because YDotNet (yrs bindings) cannot load in WASM. Two candidates: (a) a bounded JS/TS 'sync island' owning Yjs + editor binding + WebSocket, with a narrow declared JSInterop contract; (b) Ycs, a PURE C# port of Yjs, which should run under WASM and would keep the whole system in one language. Note the PRD never asks for rich text — FR-31 speaks only of a Task 'description' converging to identical text — so a plain-text collaborative editor is sufficient, which makes (b) far more tractable than a ProseMirror-class binding would be.
- (version) Verified 2026-08-17 — Azure SQL Database FREE OFFER (doc updated 2026-03-18): per database, 100,000 vCore-seconds of serverless compute + 32GB data + 32GB backup, free per month FOR THE LIFETIME OF THE SUBSCRIPTION, up to 10 General Purpose databases per subscription. 'Auto-pause until next month' mode caps at 4 vCores / 32GB, PITR limited to 7 days, LRS backup only. Minimum auto-pause delay is 15 minutes (default 60); minimum capacity configurable to 0.5 vCore. This puts the database at GBP 0 for Yello's scale.
- (constraint) COST-DERIVED ARCHITECTURAL RULE: 100,000 vCore-seconds/month is roughly 55 hours of active 0.5-vCore compute. Any unconditional periodic database access — a health check that queries, a background poller, an idle connection left open — both prevents auto-pause and silently drains the entire free allowance. Therefore NFR-2's 5-second revocation MUST be push-based (the operation that changes a Membership notifies the sync layer directly) and never poll-based. The cost model forces the better design here.
- (version) Verified 2026-08-17 — Ycs (yjs/ycs, the pure-managed-C# Yjs port, the only CRDT that could run inside Blazor WASM): NO NuGet package, NO releases at all ('There aren't any releases here'), 186 stars / 17 forks / 6 open issues, README states latest tested Yjs version 13.4.14 against a current Yjs of 13.6.32. Supports Y.Array, Y.Map, Y.Text; no Y.Xml (not needed — the PRD requires only plain text). Using it means vendoring source and owning maintenance. No alternative pure-managed C# CRDT with NuGet presence was found.
- (question) TENSION between two user decisions that must be resolved: 'C# everywhere (Blazor WASM)' and 'use a proven CRDT library rather than hand-roll the merge'. YDotNet cannot load in WASM; Ycs is pure C# but unreleased/unpackaged/stale. One of the two choices has to bend. Options put to the user: (A) bounded JS/TS sync island using Yjs, C# everywhere else; (B) vendor Ycs, truly one language, plus a hand-built collaborative plain-text editor binding; (C) compile yrs to wasm32 and P/Invoke from Blazor.
- (decision) RESOLVED (user): the merge algorithm is DEFERRED behind a single port; the seam around it is fixed now. Fixed: one WebSocket endpoint in our own container with app-level heartbeat under Container Apps' 240s ingress timeout; authorisation evaluated per inbound message and never at connect; revocation pushed not polled; persistence as an append-only per-Task change log plus a materialised plain-text projection (a shape that satisfies both a sequence CRDT and LWW, which is what makes the deferral safe); one merge port with exactly one registered implementation. The port's contract IS a conformance suite encoding FR-31, FR-33 and NFR-4, written before the implementation.
- (decision) Stated expectation in the spine (not a ban on alternatives): a plain-text sequence CRDT (RGA-style, Lamport-ordered ids, tombstones) in a SHARED C# project compiled to WASM for the client and native for the server. This is the only option giving ONE merge implementation on both ends — Yjs+YDotNet would be two implementations of one protocol that must stay compatible forever; vendored Ycs would be one but stale and unowned. Rich-text complexity does not apply: the PRD only ever requires plain text (FR-31 says 'identical final text').
- (constraint) Whole-field last-writer-wins is excluded by the PRD, not by preference, and the conformance suite is what excludes it. It fails FR-31's first testable consequence (two Users editing DIFFERENT parts both retain their changes) and fails FR-33 (5-minute disconnect reconciles with others' changes present AND own changes applied exactly once). It also reverses PRD addendum §4's documented rejection of 'presence + optimistic field updates' and would void the P3 carrier in docs/bmad-coverage.md. If LWW is ever adopted, it is a PRD amendment and bmad-prd update must run.
- (constraint) Verified 2026-08-17 — Azure Functions CANNOT hold persistent WebSocket connections; Microsoft's prescribed answer is Azure Web PubSub, which is priced out for Yello. Separately, the Azure Static Web Apps backend proxy does NOT support WebSocket ('Only HTTP requests are supported for APIs'), caps requests at 45 seconds, and 'bring your own API' requires the SWA Standard plan. Therefore the WebSocket must terminate in a container. Functions Flex Consumption free grant for reference: 250,000 executions + 100,000 GB-s/month per subscription; Always Ready instances get NO free grant.
- (decision) USER CHOSE topology: Azure Static Web Apps (Free plan) serves the Blazor WASM client; ONE Azure Container App hosts both the REST API and the sync WebSocket, scaling to zero. Keeps FR-34's revocation an in-process call rather than a distributed one. Rejected: SWA + Functions API + separate sync container (three deployables, two runtimes, FR-34 becomes cross-process); single Container App serving everything (simplest, but discards the free CDN and the split the user wanted). ACCEPTED COST: the client is cross-origin to the API, so SameSite=None + Secure cookies and CORS-with-credentials must be pinned precisely in the spine.
- (decision) USER CHOSE paradigm: vertical slices inside a hexagonal shell — Domain/Application/Infrastructure/Host rings with the dependency rule enforced by a build-failing architecture test, and one folder per use case inside Application so story-to-code mapping is 1:1. Cross-cutting invariants live in a request pipeline every slice traverses, not re-derived per slice. Rejected: Clean Architecture layered by type (a story smears across four projects); modular monolith by bounded context (Yello is arguably one context, boundaries would be ceremony and cross-module Board queries get awkward).
- (decision) USER CHOSE auth: ASP.NET Core Identity for AUTHENTICATION ONLY — Account store, password hashing with a work factor tunable without re-registration (NFR-6), cookie sessions. Identity roles, role claims and [Authorize(Roles=...)] are FORBIDDEN: they are global, and Yello's Role is per-Space. Rejected: fully hand-rolled auth (smaller surface but FR-1/FR-2 uniform-response requirements and session invalidation all land on us).
- (question) ACCEPTED RISK to record in the spine: Container Apps scale-to-zero cold start collides with NFR-5 (reads 300ms p95, writes 500ms p95), and Azure SQL auto-pause resume compounds it. Under sparse traffic most requests are cold. Mitigation options: pin min replicas to 1 (~USD 12-15/month, still inside budget) or state that NFR-5 is measured warm and the cold path is exempt. Needs a decision, not silence.

- (constraint) REVIEWER GATE FINDING (verified, critical) — SESSION_CONTEXT + connection pooling is a data-leak class, not a theoretical one. Two facts: (1) returning a connection to the pool does not itself clear session info, so setting SpaceId once per connection can serve a later request for a different Space; (2) a documented SQL Server defect (2019 CU14-CU31, 2022 CU1-CU23, 2025 RTM-CU2) means a PARALLEL plan reading SESSION_CONTEXT() on a pool-reset session can silently return another tenant's rows under RLS. Fixes applied to AD-2: set session context per unit of work with @read_only=1; database-scoped MAXDOP=1 to remove the parallel class; EF global query filters restated as an INDEPENDENT layer so neither carries NFR-1 alone; isolation suite gains a pooled-connection-reuse case. Trace flag 11042 (the documented workaround) is unavailable on Azure SQL — logged as Deferred to confirm Azure SQL's exposure.
- (constraint) REVIEWER GATE FINDING (verified) — Guid.CreateVersion7() is WRONG for SQL Server and was a defect in the first draft. SQL Server's uniqueidentifier collation orders the low-order bytes first, so UUIDv7's leading timestamp does not produce sequential index behaviour; it fragments like a v4 (a documented case had inserts go from ~20 minutes to hours). Convention corrected to EF Core's SequentialGuidValueGenerator.
- (decision) REVIEWER GATE — adversarial seam lens found four incompatible-pair holes, all closed. (1) AD-8 originally gave leases a 5s TTL, which would have required a per-connection DB read every 5s, contradicting AD-10 and the free-tier budget; leases now hold until push-invalidated, with NFR-2 met by push latency. (2) AD-10 forbade timer-driven DB access while 4.11 Notifications needs an outbox sweep; the sweep now runs at process start and piggybacks on inbound traffic, never waking an idle database. (3) AD-13 did not say when the description projection is written, allowing an eager and a lazy implementation to race; it is now recomputed in the same transaction as the append. (4) Two paths create an Account (registration, accept-invitation) and could each provision a Personal Space; AD-22 gives them one implementation and one transaction.
- (decision) RECONCILE AGAINST PRD — four quiet requirements the AD structure had dropped, now added. AD-23: account-existence non-disclosure (FR-1/FR-2/FR-10, §6.1) — uniform status, body AND duration, so registration is not an enumeration oracle. AD-24: the Space switcher and Account settings are the ONLY Account-scoped surfaces and run under an AccountScopedContext with an AccountId RLS predicate rather than bypassing AD-2 — closing the hole where 'list my Spaces' has no active Space to filter by. AD-25: NFR-8's bounds enforced as refusals at one choke point, since NFR-8 requires visible degradation. Also folded into AD-5: three non-obvious deletion behaviours (Account tombstone for attribution FR-3, Membership removal must NOT cascade to Invitations it issued FR-12, Assignee set-null never task-delete FR-21) — all three are cases where a cascade is the default reach and all three are wrong.
