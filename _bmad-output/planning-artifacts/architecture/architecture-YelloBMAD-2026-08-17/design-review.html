Yello Architecture Review

What was decided, what was rejected, what it cost — and the four things the review pass caught before they reached a story.

17 Aug 2026 25 invariants 41 FR · 9 NFR greenfield · built by dev agents

How to judge this

The spine fixes invariants, not structure. Its test is narrow: if two units one level down were built independently, could they choose incompatibly? Everything that passes that test is in. Everything else is named under Deferred and left to the code.

So the question to ask of it is not "is this how I would build Yello?" but "can a dev agent write a story-sized change that obeys every rule here and still breaks the product?" Where the answer is yes, there's a missing invariant. Four such gaps were found and closed during review; they're listed near the end.

The four forces

Most of the PRD is ordinary. Four things aren't, and they're coupled — every decision below is downstream of at least one.

FR-34 is the spine

load-bearing

A demotion or removal must land on an open editing session within five seconds, discard the unsynchronised text, and keep what was already synchronised. That single requirement kills the conventional real-time architecture — authorise at connect, then relay opaque blobs — and forces authorisation inside the sync path, on every message, against state that changes underneath it.

Isolation and cost pull opposite ways

tension

NFR-1 has no acceptable failure rate; a single verified cross-Space disclosure blocks release. Absolute isolation is easiest with hard separation — but £30/month forbids anything per-Space. So isolation must be enforced by construction inside one shared deployment, in a way a story written six months from now cannot forget.

Two ordering problems, not one

scope

Text convergence (FR-31) and Board ordering (FR-29) are distinct problems. A CRDT for the first does nothing for the second. They get separate mechanisms: a merge port, and a jittered fractional index.

The API is the isolation test

leverage

Every rule must hold on a surface with no UI to hide behind. That's a gift: it forces enforcement below the presentation layer, and it makes "the interface hid the button" an unavailable excuse.

What the constraints forced

Three decisions weren't judgement calls — the numbers made them.

You cannot buy the WebSocket

forced

Azure Web PubSub's free tier caps at 20 concurrent connections and 20,000 messages a day, one unit maximum. NFR-8 alone requires 50 concurrent Sessions per Space. Standard is roughly $49/month per unit — the entire ceiling, before compute or storage. Azure SignalR Service has the same shape.

Consequence: the WebSocket terminates in our own container. Which is where FR-34's per-message authorisation seam had to live anyway — the budget and the requirement agree.

Azure Functions cannot carry it either

forced

Functions cannot hold persistent WebSocket connections; Microsoft's prescribed answer is Web PubSub, already priced out. Separately, the Static Web Apps backend proxy states plainly that only HTTP requests are supported for APIs — WebSocket, for example, is not supported, caps requests at 45 seconds, and requires the Standard plan.

Consequence: the API and the sync endpoint share one Container App. Splitting them would make FR-34's revocation a cross-process, cross-runtime concern — turning the product's most important requirement into a distributed one.

The database is free, permanently — with a rule attached

favourable

The Azure SQL Database free offer gives 100,000 vCore-seconds, 32 GB data and 32 GB backup per month for the lifetime of the subscription. That's about 55 hours of active half-vCore compute a month.

So anything touching the database on a timer — a health check that queries, a background poller, a connection that never idles out — both prevents auto-pause and silently drains the entire allowance.

Consequence: NFR-2's five-second revocation cannot be polled. The operation that changes a Membership pushes the notification. The cost constraint forces the better design — and it's a rule a dev agent would otherwise break on story three, with nobody noticing until the bill.

The decisions

Each of these was a real fork with a real cost. The rationale lives here; the spine itself records only the rule.

.NET 10 LTS, C# everywhere

stack
Chosen.NET 10.0.11 LTS server, Blazor WebAssembly client.
RejectedTypeScript end-to-end with Yjs; a .NET backend with a React client.
Cost accepted: the CRDT ecosystem is far thinner on .NET. YDotNet — bindings over Rust yrs — sees about 85 downloads a day against Yjs's 920,000 a week, and its own README says it is early with an API subject to change. More sharply: it ships Windows, Linux and macOS natives only, so it cannot load in WebAssembly at all.

The merge algorithm is deferred behind a port

AD-12

Choosing Blazor WASM and "use a proven CRDT rather than hand-roll" put two decisions in direct conflict: the good library can't run in the browser, and the only pure-C# port (Ycs) has no NuGet package, no releases at all, and is tested against a Yjs six minor versions old.

Fixed nowTransport, the per-frame authorisation seam, push-based revocation, append-only persistence, and one merge port.
DeferredWhat actually merges. The port's contract is a conformance suite encoding FR-31, FR-33 and NFR-4, written first.
This is safe only because the persistence shape — an append-only change log plus a derived projection — satisfies both a sequence CRDT and last-writer-wins. Swapping later is a registration change, not a migration.

Last-writer-wins is excluded — by the tests, not by decree

contested

LWW was raised as a simpler option. It fails two testable PRD consequences outright:

  • FR-31: "two Users editing different parts both retain their changes" — whole-field LWW overwrites one entirely.
  • FR-33: after a five-minute disconnect, your changes apply exactly once and theirs are present — LWW can deliver one or the other, never both.

It also reverses the addendum's own documented rejection of "presence + optimistic field updates", and voids the P3 carrier in the coverage tracker.

Framed correctly: adopting LWW is a PRD amendment, not an architecture decision. The conformance suite is what enforces this, so no story can adopt it quietly.

Azure SQL serverless, with row-level security as the isolation floor

AD-2

RLS turns out to produce exactly the error semantics FR-15 demands, rather than the code having to remember them: out-of-Space rows are invisible, so a cross-Space request naturally 404s; a within-Space wrong-role request still sees the row, so the application returns 403.

Cost accepted: local parity needs a SQL Server container rather than the same engine. Azure SQL Developer — the actual cloud engine in a local container — would remove that cost entirely, but it was still private preview and credential-gated as of 23 July 2026. Logged as Deferred.

The mechanism that matters

FR-34 is what the PRD says the product should be judged on. Everything in the sync design exists to make this one sequence true.

What review caught

The gate ran a rubric walk plus two adversarial lenses: verify every named technology against the live web, and construct two units that obey every rule and still build incompatibly. It found six things worth reporting. Two were defects in the draft itself.

SESSION_CONTEXT under connection pooling is a live data-leak class

critical

Two compounding facts. Returning a connection to the pool does not itself clear session state, so setting the Space once per connection can serve a later request for a different Space. And a documented SQL Server defect — 2019 CU14–CU31, 2022 CU1–CU23, 2025 RTM–CU2 — means a parallel plan reading SESSION_CONTEXT() on a pool-reset session can return another tenant's rows silently and successfully under RLS.

Fixed in AD-2: session context set per unit of work with @read_only = 1; database-scoped MAXDOP = 1 to remove the parallel class outright; EF global query filters restated as an independent second layer so neither carries NFR-1 alone; and a pooled-connection-reuse case added to the isolation suite. The documented trace-flag workaround isn't available on Azure SQL, so whether Azure SQL is affected at all is logged as an open item.

UUIDv7 was wrong, and it was mine

fixed

The first draft specified Guid.CreateVersion7() for all ids. SQL Server's uniqueidentifier collation orders the low-order bytes first, so a v7's leading timestamp buys nothing — it fragments an index exactly like a v4. A documented case had inserts go from about twenty minutes to hours.

Corrected to EF Core's SequentialGuidValueGenerator.

Four seams where obedient units still diverge

closed
  • Lease TTL contradicted the cost rule. A five-second TTL implied a database read per connection per interval — exactly what AD-10 forbids. Leases now hold until push-invalidated.
  • The outbox needed a poll that AD-10 banned. Resolved by having the recovery sweep run at process start and piggyback on inbound traffic, so it never wakes an idle database.
  • Nobody owned when the description projection is written. An eager and a lazy implementation would race. Now recomputed in the same transaction as the append.
  • Two paths create an Account. Registration and accept-invitation could each provision a Personal Space. AD-22 gives them one implementation and one transaction.

Four requirements the AD structure had dropped

added
  • AD-23 — account-existence non-disclosure. Registration, authentication and invitation must be identical in status, body and duration; otherwise registration is an enumeration oracle. Two slices would certainly have differed on returning 409.
  • AD-24 — "list my Spaces" has no active Space to filter by, so it had no defined home under RLS. The Space switcher and Account settings are now the only Account-scoped surfaces, running under an AccountId predicate rather than a bypass.
  • AD-25 — NFR-8's bounds enforced as refusals at one choke point. NFR-8 requires visible degradation; nothing said where.
  • AD-5 — three deletion behaviours where a cascade is the obvious reach and all three are wrong: Account tombstones preserve attribution, removing a Membership must not delete Invitations it issued, and losing an Assignee nulls the field rather than deleting the Task.

Still open

Three of these change the build. The rest can wait for evidence.

  • Cold start. Pin a warm replica, or declare NFR-5 measured-warm and exempt the cold path. Either is defensible; silence isn't.
  • Azure SQL's exposure to the SESSION_CONTEXT defect. MAXDOP = 1 is cheap insurance at this scale, but it's worth knowing whether it's needed.
  • The PRD's six open questions are untouched by this spine — ownership transfer without acceptance, the revocation budget, and whether the NFR-8 bounds are defensible all remain product calls.
