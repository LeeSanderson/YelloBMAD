# Spine Pair Review - Yello

## Overall verdict

This is an unusually disciplined first draft: nine flows complete, every `{token}` reference resolving, canonical section order intact, and a decision record that genuinely explains the load-bearing choices rather than decorating them. Three things stop a downstream consumer source-extracting cleanly — the Component Patterns table contains four duplicate/overlapping rows with no precedence rule, the light theme has hex values but no component-level resolution mechanism, and the "Verified contrast" table's numbers are estimates presented as verification (8 of 12 rows are arithmetically wrong). Beyond that, two of the nine IA surfaces — Space settings and Project settings — carry almost no behaviour, which leaves FR-12, FR-13 and FR-14 with no affordance to build against despite FR-14 being the trigger of UJ-6.

## 1. Flow coverage - strong

Extracted all eight UJ names from PRD §3.3 and checked each against EXPERIENCE.md § Key Flows for a named protagonist, numbered steps, an explicit climax beat and a failure path. All eight are present and structurally complete; UJ-9 is net-new and intentional. Every PRD-stated edge case is carried: UJ-1's duplicate-address uniformity, UJ-2's both cases, UJ-3's revocation and scanner/prefetch/forward, UJ-4's deep link, UJ-5's forty-second drop, UJ-6's demotion variant, UJ-7's both, UJ-8's decline/lapse and 409. Protagonists match the source including the accent on Tomás. No misses.

### Findings

- **low** UJ-6 is the only flow carrying a *Variant* rather than a *Failure* (EXPERIENCE.md:368). This is faithful to the source — PRD UJ-6's single edge case *is* the demotion — so it is not a coverage miss. The genuinely unhandled composition is filed under §4. *Fix:* none needed here; see §4's first finding.
- **low** Two of the eight titles are not verbatim despite the header claiming they are: PRD "UJ-3. Nadia accepts an invitation…" → EXPERIENCE.md:331 "an Invitation" (an improvement in glossary discipline, but the claim is still false), and PRD "UJ-5. …at the same time" → EXPERIENCE.md:351 "…at once". EXPERIENCE.md:308 asserts "UJ-1 … UJ-8 are PRD §3.3 verbatim". *Fix:* restore both titles exactly and raise the UJ-3 capitalisation as a PRD glossary defect instead, or soften the claim to "IDs and protagonists mirror the source".

## 2. Token completeness - adequate

Extracted 220 frontmatter token paths and every `{path.to.token}` reference in both files: 67 distinct in DESIGN.md, 10 in EXPERIENCE.md. **All resolve.** The single unresolved string is `{path.to.token}` at EXPERIENCE.md:13, which is a syntax illustration and not a reference. All 14 colour roles carry both a hex value and a light/dark pair — no CRITICAL colour gaps. Contrast ratios were recomputed independently from the hex values using WCAG relative luminance (0.2126R + 0.7152G + 0.0722B over sRGB-linearised channels, threshold 0.03928) and (L₁+0.05)/(L₂+0.05).

  No error flips a pass into a fail, and the 1.1:1 card-to-column step (1.085) and the light-theme claims at DESIGN.md:287 are directionally right — so no design change follows. But three rows are *overstated*, and the two light-theme rows sit only 0.06 and 0.06 above the 3:1 gate on numbers that are already optimistic. No alternate luminance formula (γ2.2, the 0.04045 threshold, a different ground) reproduces the pattern, so these were estimated rather than computed. *Fix:* replace all twelve with computed values and state the formula used, so the accessibility reviewer at Finalize is checking arithmetic rather than redoing it.
- **high** The light theme has no component-level resolution. `components.*` (DESIGN.md:110-227) references dark tokens exclusively, and **11 of the 14 `-light` colour tokens are referenced nowhere in either file** — only `surface-card-light`, `surface-column-light` and `border-hairline-light` appear, and only inside the one-sentence light contrast note. DESIGN.md:250 asserts "Both themes are peers at runtime", but a consumer extracting the component token map gets a dark-only system whose light counterpart exists solely as a prose naming convention. *Fix:* one explicit sentence in § Colors stating the resolution rule — "in light mode every `{colors.x}` reference in `components` resolves to `{colors.x-light}`" — which is mechanically applicable and costs nothing.
- **medium** `{colors.danger}` is used against DESIGN.md's own two rules for it. § Colors:265 restricts it to "destructive only", and Do's and Don'ts:387 says "Reserve `{colors.danger}` for the genuinely irreversible / Don't use danger for validation errors or ordinary refusals" — yet `components.description-editor-inert` (DESIGN.md:200-203) gives the FR-34 revocation state a danger border. Losing access is a refusal. An implementer following the Do/Don't table would not use danger there; one following the component token would. *Fix:* either carve out the exception explicitly ("and for the FR-34 inert state, because the unsynchronised text is genuinely lost") or introduce a separate border token.
- **medium** Three off-scale pixel literals inside a document that asserts a strict 3px scale (DESIGN.md:321, "3 / 6 / 9 / 12 / 18 / 24 / 36"): `spacing.card-pad-x: 10px` (:100), `button-primary`/`button-danger` `padding: '{spacing.2} 13px'` (:170, :175), `avatar size: 20px` (:157). Worse, `10px` then appears as a *bare literal* in `context-bar.padding` (:136) and `space-switcher.row-padding` (:186) — bypassing `{spacing.card-pad-x}`, which is defined as exactly that value. *Fix:* reference `{spacing.card-pad-x}` in those two, and either add scale rungs for 10/13/20 or state in § Layout & Spacing that component-internal horizontal padding is off-scale by intent.
- **medium** Every font size is an absolute px value (DESIGN.md:41-81), including `role-label` at **9px** and `meta` at **10px** — and those two carry the Role chip and all metadata, which UJ-4 and NFR-9 make load-bearing. Neither spine says whether these are rem-equivalent or how they behave under a user font-size setting. Page zoom scales px, so WCAG 1.4.4 is probably satisfied, but text-only resize is not, and 9px is the permanent Role indicator on a consumer-stakes product. *Fix:* state the px↔rem convention and set a floor below which the Role chip does not shrink.
- **low** `colors.role-chip` `#241F52` sits at **1.05:1** against `colors.surface-card` `#18213C`, which is the context-bar ground (`components.context-bar.background`, DESIGN.md:133), and the chip carries no border. The chip fill is invisible; only its text does any work (8.56:1, comfortably fine). Same in light: 1.29:1. Not a WCAG failure — the chip is display-only and its text passes — but "monospace, uppercase, 2px corners" describes a chip an implementer cannot see. *Fix:* either give `role-chip` a hairline border or drop the fill and specify it as tracked mono text.
- **low** `spacing.unit: 3px` duplicates `spacing.1: 3px`, and `spacing.1`, `spacing.4`, `spacing.7` are declared but unused by any component. Harmless for a scale; noted only so a token-pipeline author is not hunting for a distinction that is not there.

## 3. Component coverage - thin

Extracted 23 component names from DESIGN.md frontmatter, 20 bullets from § Components (`column-count` and `description-editor-inert` are specified inside their parent bullets, which is fine), and 22 rows from EXPERIENCE.md § Component Patterns. Every DESIGN.md component has a real visual spec — anatomy, ground, radius, typography — with no one-word entries. The EXPERIENCE.md side does not hold up as cleanly.

### Findings

- **high** § Component Patterns contains **four duplicate rows with no precedence rule**: `Task detail` appears at both EXPERIENCE.md:128 and :141, and `Description editor` at both :129 and :142. The pairs do not contradict but they are not the same either — :141 adds focus return to the originating card, :142 adds AD-13 frame batching, and each omits what the other has. A consumer asking "what is the behavioural rule for Description editor?" finds two answers. This looks like the artifact of the self-run Pass 1 fix recorded at `.memlog.md`:34, which added missing rows without deduplicating against existing ones. *Fix:* merge each pair into one row; the union of the two is correct in both cases.
- **high** No component pattern exists for changing a Role, removing a Membership, or issuing/revoking an Invitation (FR-13, FR-14, FR-12). FR-14 is the causal trigger of UJ-6 — which the PRD flags at FR-34 as "the acceptance criterion this product should be judged on" — and UJ-6:363 simply says "Ravi removes her Membership" with no affordance behind it. FR-13 also carries non-obvious Role-scoped narrowing (an Admin may only offer Member↔Viewer; only an Owner may touch Admin; no change may produce a second Owner), and the `Picker` row at :143 names only Assignee/Label/Status, so the Role picker is not covered by it either. *Fix:* add three rows — Membership row, Role picker, Invitation row — with the FR-16 narrowing stated on the Role picker.
- **medium** Component names are not identical across the pair. DESIGN.md specifies one `picker` ("One visual treatment for Assignee, Label and Status", :369); EXPERIENCE.md names four things — `Assignee picker` (:131), `Label picker` (:132), `Status control` (:133) and `Picker (Assignee / Label / Status)` (:143) — and `Status control` recurs in Responsive & Platform:263 with no DESIGN.md counterpart under that name. Likewise DESIGN.md's `bulk-move-bar` appears in EXPERIENCE.md as both `Bulk move` (:134) and `Bulk move bar` (:144). *Fix:* collapse to the DESIGN.md names — `picker` and `bulk-move-bar` — and express the three uses as a Use column value rather than as separate components.
- **medium** The Task card metadata row has no overflow discipline. DESIGN.md:353 loads it with Label chips + Presence indicator + Assignee avatar, `label-chip` is user-defined per Space with unbounded name length and count (FR-22), and NFR-8 permits 10 concurrent editors per Task — so "2 editing" becomes "10 editing" and an arbitrary number of chips compete for a 13px-title card at the density FR-28 requires. Neither spine states a truncation, wrap, or "+N" rule for either. *Fix:* one line in the Task card row: max chips rendered, overflow treatment, and the Presence count's display form at the NFR-8 bound.
- **low** `task-card-lifted`, `drop-zone`, `focus-ring`, `button-primary` and `button-danger` have DESIGN.md specs but no § Component Patterns row. Their behaviour is genuinely covered elsewhere — Interaction Primitives:180-188, Accessibility Floor:249, State Patterns:154 — which is the right home for it. Noted only because a consumer walking the Component Patterns table as an index will conclude they are unspecified. *Fix:* a one-line pointer under the table naming where those five live.

## 4. State coverage - thin

Walked all nine IA surfaces (EXPERIENCE.md:31-41) against the applicable state set and checked each against the 24 rows of § State Patterns. Task detail and the Board are genuinely exhaustive — access-ended, demotion, disconnection, failed reconciliation, deleted-while-open, scale at 5,000, cold load, keyboard focus — and each row traces to a specific FR or AD. The two settings surfaces and three cross-cutting states are where it thins out.

### Findings

- **high** Revocation-while-disconnected is unhandled, and the two rows that would compose to cover it contradict each other in committed copy. :152 promises "Disconnected. Your changes are held locally." :150 requires that on access ending the unsynchronised text "**is not applied**" while staying visible "with the banner stating it was not saved" — and :150's mechanism is a push (AD-9) that by definition cannot reach a disconnected client. So: Beatriz drops, is told her changes are held, is removed while offline, reconnects, and the product must now retract a promise it made in writing. This is the composition of FR-33 and FR-34, the seam PRD §4.9 calls out as "the requirement most likely to be got wrong". Neither spine addresses it. *Fix:* a State Patterns row for reconnect-after-revocation, and soften :152's copy so it does not promise application ("held locally" → "not yet sent").
- **high** Space settings (:39) and Project settings (:40) carry almost no behaviour. Between them the State Patterns table gives Space settings two rows (offer pending as Owner, delete Space) and Project settings one (delete Project). Missing across both: any empty state; the Membership list at NFR-8's 100-Membership bound; FR-12/FR-13/FR-14 affordances and their confirmations; and — most significantly — **what happens to a user sitting on either surface when their own Role drops below Admin.** Foundation:27 states the principle ("the interface has to be built to be interrupted") and AD-9 pushes the change, but only the Task editor has an interruption state. A whole surface disappearing under someone is the general case of FR-34 and it is uncovered. *Fix:* one State Patterns row for "Role drops below the surface's requirement while viewing it", plus states for the three Membership operations.
- **high** Membership removal is absent from the destructive-confirm blast-radius ladder. :136 enumerates "Task, Project, Space, Account" and FR-14 — the operation that ends someone's access to everything in a Space, immediately, with a live editor open — is not on it. *Fix:* insert Membership between Task and Project, and state whether removing someone mid-edit warns the remover that a session is live.
- **high** Session expiry has no state anywhere. **`Session` appears exactly once in EXPERIENCE.md — at :15, in the declared vocabulary list — and never again.** FR-2 requires that "a Session that has expired or been invalidated grants access to nothing", and AD-7's cookie is the only credential. A user whose Session expires mid-Board is a guaranteed daily occurrence and the spine says nothing about what they see, where they land, or whether their local replica survives (AD-11 makes that a real question). *Fix:* one State Patterns row on the Any surface, covering the landing surface and the fate of unsynchronised replica state.
- **medium** Offline is designed only inside the Task editor. §8 requires Yello "degrades honestly without" connectivity, and the Board is a live surface — Presence, pushed permission changes, other people's Task moves. A user on the Board with a severed `/sync` gets no treatment. Both example spines carry a global offline row for exactly this. *Fix:* one row for disconnection on a non-editor surface, stating what stops updating and how the user knows.
- **medium** § Status Configuration (:212-237) has no in-flight and no refused state, while the structurally smaller bulk move has both. The FR-27 Space-level removal commits "the removal, the Space-wide mapping and every per-Project exception" as one transaction (:233) across up to 50 Projects × 5,000 Tasks — strictly larger than the bulk move that earned "Moving 4,812 Tasks." on precisely this reasoning (`.memlog.md`:31). *Fix:* extend the two bulk-move rows to cover the Space-level Status migration, or add the equivalent pair.
- **medium** The List View has no scale state. FR-30 explicitly requires the List View to hold NFR-5 and NFR-9 at 5,000 Tasks "on the same terms as FR-28", but the "Board at scale" row (:157) names the Board only, and FR-30 is the one FR with a dedicated IA surface that neither spine cites anywhere. Interaction Primitives:207 gives "the List View pages" and nothing else — no page size, no keyboard row traversal, no filter/sort control spec. *Fix:* a List View at-scale row mirroring :157, and a filter/sort control in Component Patterns.
- **medium** The 403 state is named but not designed. § Isolation and Refusal gives the two 404 cases eight hard rules; the 403 row (:103) gets six words — "A permission statement naming the capability" — with no copy, no surface and no placement. Worse, Voice and Tone:76 lists *"You don't have permission to view this Task."* in the **Don't** column, unqualified, which reads as a ban on exactly what :103 requires. *Fix:* qualify the Voice row as "for a cross-Space miss" and give the 403 one worked copy example.
- **medium** The Unauthenticated surface has no state for an Invitation opened while signed in as a different Account. AD-28 authorises acceptance "on the authenticated Account matching the address the Invitation names", and UJ-3:339 mentions only that "an existing-Account invitee gets an explicit confirmation". Opening a forwarded or personal-address invitation while logged in as someone else is the most common real-world invitation failure, it sits on NFR-9's gated invitation flow, and it is unhandled. *Fix:* one row — what the invitation view shows, and whether it offers to switch Account.
- **low** Registration and sign-in are the only submit-and-wait interactions in a product that states "There is no save button anywhere in Yello" (:25), and AD-23 deliberately makes registration *slow* by performing the password hash even for a known address. There is no in-flight state for the one place a user waits on a round trip. *Fix:* add the submit state to the Cold load row or its own.

## 8. Shape fit - strong

DESIGN.md carries all eight canonical body sections in canonical order — Brand & Style, Colors, Typography, Layout & Spacing, Elevation & Depth, Shapes, Components, Do's and Don'ts — with subsections nested rather than interleaved. EXPERIENCE.md carries all eight required defaults (Foundation, Information Architecture, Voice and Tone, Component Patterns, State Patterns, Interaction Primitives, Accessibility Floor, Key Flows) and both triggered sections: Responsive & Platform (three breakpoints, correctly triggered by responsive web) and Inspiration & Anti-patterns (correctly triggered — Trello is named at all three layers, and the section splits cleanly into lifted / must-not-follow / must-beat).

**On the Motion extension: legitimate, not a violation.** The order lock binds the eight canonical sections relative to each other, and Motion is appended *after* all eight rather than inserted among them, so the lock holds. The `motion` frontmatter group is the same shape as any other token group, is referenced from both files (`{motion.lift}`, `{motion.settle}`, `{motion.long-press-threshold}`), and the spec's frontmatter table is not declared closed — `components` already demonstrates arbitrary nesting. The product justification is real: an unspecified motion budget means each developer invents timing, and the 90–120ms figure is coherent with AD-11 rather than arbitrary. DESIGN.md:393 pre-empts the objection explicitly. Keep it.

**On the three strong invented sections.** *Space Context and Role Legibility* earns its place — it holds the product thesis plus two hard rules (absent-not-disabled; switching carries nothing over) that no standard section owns, and it is cited by name from three other sections. *Isolation and Refusal* earns it strongly — a 404/403 table plus five hard rules is neither copy (Voice) nor per-surface behaviour (State Patterns), and the security consequence justifies the prominence. *Status Configuration* earns it — FR-27's cascade is an ordered multi-step procedure that no table row can hold.

### Findings

- **medium** § Internationalisation does not earn its place and should fold. Of its six bullets: RTL and logical properties belong in **Responsive & Platform** (it is a layout-direction rule and that section already owns layout behaviour); the server-clock rule for relative time is a genuine behavioural obligation on the Offer dialog and belongs in **State Patterns** or the Offer indicator row, where an implementer will actually meet it; "translate glossary terms once" belongs in the **vocabulary note at :15**, which is where §2's no-synonyms discipline is already declared; and the remaining three are duplication of DESIGN.md:317, a pointer to DESIGN.md § Typography, and a build convention. Distributed, every obligation lands closer to the code that must honour it — which is the section's own stated reason for existing ("the obligations need stating or they will not be met"). As a section it is the one place a consumer can skip without losing anything they will not meet elsewhere. *Fix:* fold as above and delete the heading.
- **low** § Motion is where the DESIGN/EXPERIENCE boundary leaks. It carries behavioural rules that EXPERIENCE.md already owns: the long-press scroll-versus-lift rule (DESIGN.md:399 vs EXPERIENCE.md:184) and the `prefers-reduced-motion` rule, which appears near-verbatim in both files (DESIGN.md:405, EXPERIENCE.md:252). "Never animated: … a permission change taking effect" (:403) is a behavioural constraint on FR-34, not a visual spec. *Fix:* keep the durations and easings in DESIGN.md; move the three behavioural clauses to Interaction Primitives and Accessibility Floor, leaving pointers.
