Key screen — Status configuration and the FR-27 cascade

The rule this screen exists to enforce: the interface must not decide anything. PRD §11 records that FR-27's original defect was that its rename half asked while its removal half guessed — affected Tasks fell to a Project's first Status. Both halves now report and ask, and a default selection in any destination picker would reintroduce the guess.

Also visible: why the Status delta editor must show which entries come from the Space defaults and which from this Project's delta. Without that distinction, the cascade below is incomprehensible when it fires.

3 · Space-level removal — report and ask

The hard half. Removing a Status at Space level takes one Space-wide destination, then reports every Project that cannot accept it and requires a destination drawn from that Project's own post-removal set. Nothing applies until every reported Project has one.

Five things here are requirements, not layout choices. Every affected Project is named and carries how many of its Tasks are affected. The two unset pickers read “Choose…” and not a pre-filled value — there is no fallback and no silent placement. The commit is disabled and says why, because nothing applies until every reported Project has a destination. And the whole thing is one transaction: the removal, the Space-wide mapping and every per-Project exception apply together or not at all. FR-26 · FR-27 · AD-17

Always satisfiable, so this dialog can never trap the Owner: a Project's effective Status set can never be empty (FR-25), so a valid destination always exists in every affected Project.
