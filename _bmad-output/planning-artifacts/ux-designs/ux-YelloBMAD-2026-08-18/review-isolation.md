# Isolation Review — does any UX decision leak across a Space boundary?

## Overall verdict

**No specified leak.** Both spines are unusually disciplined about isolation for a UX document — the `Isolation and Refusal` section, the switcher's identity-only austerity, the deliberate placement of the Ownership Offer indicator on the Space context bar rather than the switcher, and the explicit "live regions carry no cross-Space information, ever" are all correct and several of them anticipate attacks a UX spec normally misses. The danger is entirely category (b): **the spines specify the server-facing half of isolation and are almost silent on the client-facing half.** Nineteen findings follow, of which two are critical — the lifetime of the client-side local replica (AD-11) across a Space switch, sign-out and revocation is never specified, and EXPERIENCE.md asserts "same latency" for the two 404 cases while AD-20's refusal record makes one of them provably slower. Neither would be caught by SM-1's isolation suite as currently scoped, which is what makes them the two most likely routes to a verified cross-Space disclosure in a shipped build.

Counts: **2 critical, 7 high, 4 medium, 6 low.**

---

## 1. Error and refusal copy

**Verdict: the copy is right; the two non-copy dimensions the section itself names — latency and page-vs-toast — are the exposed ones, and one of them is broken upstream.** `Not available.` genuinely discloses nothing, the "not a toast" rule is correct, the "route back never to a remembered last-Space" rule is a real catch, and "the client owns the string" closes the templated-prose hole. But the section states properties it cannot enforce and assigns them to nobody.

- **[critical]** The two 404 cases cannot have equal latency as implemented (EXPERIENCE.md `Isolation and Refusal`, line 105 — *"same words, same layout, same latency"* — against ARCHITECTURE-SPINE AD-20). *What leaks:* existence across a Space boundary, by timing. AD-20 requires the pipeline to write an `AccessRefusal` row for **every Space-boundary 404** and not for an ordinary not-found. A boundary 404 therefore performs a database INSERT inside the request that the "resource genuinely does not exist" case does not. That is a measurable difference, repeatable, and available to an unauthenticated-adjacent attacker holding only a Membership in one Space: probe an id, time the refusal, and learn whether the id exists somewhere in Yello. NFR-1's "existence is never disclosed across a Space boundary" fails, and AD-3 — unlike AD-23 — never makes duration part of its contract, so nothing upstream catches it. EXPERIENCE.md asserts the property, which a reasonable implementer reads as satisfied-by-construction. *Fix:* make the latency obligation an owned mechanism, not an assertion. Either (a) write the refusal record outside the response path (enqueue, flush after the response is sent — note AD-10 permits piggybacking), or (b) write an equivalent record for the ordinary not-found case so both pay the same cost, or (c) state explicitly in AD-3 that boundary refusals are padded to a fixed floor. Whichever is chosen, EXPERIENCE.md should cite it rather than assert the outcome, and the isolation suite should gain a *timing* case — SM-1 currently measures disclosure, not duration.
- **[high]** `409, never 404` is stated without the Membership qualifier, twice (EXPERIENCE.md State Patterns line 161, and UJ-8 failure path line 390). *What leaks:* Ownership Offer existence across a Space boundary. AD-26 says 409 rather than 404 is correct *because* "the caller holds a Membership in the Space, so AD-3's boundary rule does not apply" — the qualifier is load-bearing. Both spine statements drop it and read as absolutes. An implementer building the offer-transition endpoint from the UX spine returns 409 for any offer id that is not `Pending`, including one belonging to a Space the caller has no Membership in. The endpoint becomes a cross-Space existence oracle: 409 means an `OwnershipOffer` row with this id exists somewhere in Yello, 404 means it does not. *Fix:* restate both lines as "409 once the Space boundary has been cleared; a boundary miss is still 404 (AD-3)". The check order is the whole finding — resolve `ActiveSpaceContext` first, evaluate `State = Pending` second, and never the reverse.
- **[medium]** A boundary 404 arriving in response to an *optimistic* write has no specified state (EXPERIENCE.md `Interaction Primitives` line 208 — everything non-destructive is optimistic by default — against `Isolation and Refusal` line 112, "It is **not** a toast"). *What leaks:* nothing directly; this is a correctness hole that pushes the implementer toward one of two rule violations. A user switches Space, creates a Task, and the write 404s because their Membership was removed a second earlier. The only two natural implementations are a silent revert — which breaches FR-34's observability and NFR-8's "degrade visibly, never silently" — or a toast, which the Isolation section explicitly forbids. *Fix:* add a State Patterns row. An optimistic write refused by a boundary 404 should collapse to the same terminal treatment as any other boundary refusal: revert the replica, then render the full `Not available.` surface with the route back. It is a final answer, not a retryable fault.
- **[medium]** Cold load renders the context bar — and therefore the Space name — before authorisation for the request resolves (EXPERIENCE.md State Patterns line 174: *"the context bar can render before its contents"*). *What leaks:* a Space name for a Space the caller may no longer belong to, sourced from client state rather than from the server. The name cannot come from a 404 (AD-3 strips it), so it can only come from a cache — which means the context bar distinguishes "removed from" (name available locally) from "never existed" (no name), breaking line 105's "identical in every respect", and on a shared browser profile it renders one Account's Space name to another. It also contradicts AD-1's "never inferred from a prior request". *Fix:* the context bar may render its *shell* before contents, never its Space name. The name is gated on the current request's Membership resolution for that Space. Compose this with finding 5.1.
- **[low]** The 403 has no approved copy exemplar anywhere in either spine. *What leaks:* nothing — "a permission statement naming the capability" (line 103) is safe by construction, because AD-3 guarantees a 403 only ever reaches a caller who already holds a Membership in that Space, so naming the capability, and even naming the object, discloses nothing they are not entitled to. The gap is that the Voice table's only permission-refusal string (*"You don't have permission to view this Task."*, line 75) appears in the **Don't** column, so an implementer hunting for 403 copy finds only a banned string and invents one. *Fix:* add one approved 403 exemplar to the Voice table, e.g. `Viewers cannot edit Tasks.` — capability-shaped, not object-shaped, which also keeps it reusable and i18n-cheap.
- **[low]** A 403 on an Ownership Offer transition by a non-recipient Member could confirm a pending offer exists. *What leaks:* within-Space only, so **not** an NFR-1 breach — recorded for completeness. Space settings is Owner/Admin only and the indicator appears "only for the named recipient", so an ordinary Member is not entitled to know an offer is pending or that it is not theirs. A 403 naming the capability tells them both. *Fix:* a non-recipient's attempt on an offer transition returns the same 409 as any other non-actionable transition, or a 404. Never a Role-shaped 403 — AD-26 decides this by row identity, so a Role-shaped refusal is the wrong shape anyway.

## 2. ARIA live regions

**Verdict: the rule is stated correctly and the two mechanisms most likely to break it are unaddressed.** Line 253 — *"Live regions carry no cross-Space information, ever. An announcement is a disclosure surface like any other (NFR-1)"* — is exactly right and rare to see written down. Neither spine then works out what could put cross-Space content into one.

- **[high]** Multi-tab is never considered anywhere in either spine, and FR-34 pushes the implementer straight into it (EXPERIENCE.md `Accessibility Floor` line 247, assertive permission-change announcements; `Space Context and Role Legibility` line 65, "switching Space carries nothing over"). *What leaks:* a Space name, and the fact of a Membership change in it, announced into a surface scoped to a different Space. A single Account can hold two tabs open on two different Spaces — not a cross-Space view, but a state the spines never name. AD-9 publishes `MembershipChanged(AccountId, SpaceId)`; AD-8 leases are per connection. An implementer chasing "the effect is observable without the affected participant acting" will reasonably fan the notice out to every tab via a BroadcastChannel or shared worker, and having done so will need to disambiguate *which* Space ended — so the announcement becomes "Access to Northwind Redesign ended." That string, spoken in the tab showing Ravi's Space, is a Space name crossing a boundary through the assertive live region. Screen-reader users take the disclosure first and hardest, which inverts the intent of line 247. *Fix:* state that a permission-change notice is delivered only to the client context whose active Space matches the change, that cross-tab fan-out is a per-tab filter and never a shared announcement, and that the copy stays `Access ended.` with no Space name in any case. Add a multi-tab clause to line 65: each tab holds its own Space context and they share no state.
- **[high]** Inbound frames and pending announcements queued before lease invalidation have no specified disposal (EXPERIENCE.md State Patterns line 150 `Access ended mid-edit`; UJ-6 steps 3-4; `Accessibility Floor` line 246 Presence polite). *What leaks:* who was present in, and what was edited in, a Space in the moments *after* the caller's access ended. FR-34 and AD-8 are thorough about the outbound direction — a client frame arriving on an invalidated lease is discarded, "including via any delayed or retried frame". Nothing in either spine covers the *inbound* direction: frames already delivered to the client and sitting in a render or announcement queue when the lease dies. The polite Presence region then announces "Ravi is editing" or a remote description edit renders, one tick after `Access ended.`, for a Space the Account now has no Membership in. NFR-1's "a failure, timeout or partial response never discloses data or existence across a Space boundary" fails, and it fails on the one requirement the PRD names as the criterion the product should be judged on. *Fix:* add to the `Access ended mid-edit` row: on lease invalidation the client discards every queued inbound frame for that Space, clears both live regions, and suppresses further announcements before the assertive `Access ended.` is announced. The purge is ordered *before* the banner, not after.
- **[medium]** The Presence announcement's content is unspecified. *What leaks:* potentially an email address — see 4.1, which is the same defect surfacing through a different component. The display-name case is fine: Presence shows only Memberships of the same Space (FR-32) and roster names are visible to every Role via the Assignee picker, so announcing a display name discloses nothing new. *Fix:* specify the announcement string as display-name-or-count only, explicitly never an address.
- **[low]** FR-32's "Presence never reveals an Account's activity in any other Space" is not restated in either spine. *What leaks:* nothing, in practice — Presence is derived from sync-channel participants, each of whom holds a lease for `(Account, SpaceId)`, so same-Space scoping holds by construction. The Assignee picker gets its FR-21 constraint restated (line 131) and Presence does not, which is an asymmetry worth closing while it is cheap. *Fix:* one clause on the Presence indicator row.

## 3. The Space switcher

**Verdict: correctly handled, and consistently so — this is the strongest part of the review.** Four independent statements agree that the switcher returns identity only (EXPERIENCE.md IA line 47, Component Patterns line 126, UJ-4 step 2, DESIGN.md `space-switcher` line 366), and IA line 47 explicitly pre-empts the exact attack — *"A switcher that badges a Space with '3 Tasks' or 'offer pending' breaches NFR-1."* The Ownership Offer indicator lives on the Space context bar in every one of the five places it is mentioned, always qualified to the active Space, and UJ-8 step 3 explicitly requires Nadia to *be in that Space* to see it. No contradiction exists anywhere in either spine. The findings below are about the two Account-scoped surfaces that are **not** the switcher.

- **[high]** Three specified Account-scoped reads are richer than AD-24's "identity only", and none is flagged. *Locations and mechanisms:* (i) State Patterns line 167, `Delete Account refused` — *"Name every Space still owned"* requires filtering the Account's Spaces by `Role = Owner`, which is a **Membership** attribute read at Account scope; AD-24 says "no Project, Task, Membership, Label or count crosses a Space boundary through them." (ii) State Patterns line 172, `Scale bound reached` on "Any creation surface" — NFR-8 bounds *Spaces per Account* at 50, so stating that bound plainly on the Space-creation surface requires an Account-scoped **count** across Spaces, and Space creation is not one of AD-24's two enumerated surfaces. (iii) UJ-7 step 4 makes a virtue of the Token's capability being "his *current* Role in that one Space… so a later demotion narrows the Token", which invites the Account settings Token list to render a per-Space **Role** — again a Membership crossing a boundary through an Account-scoped surface. *What leaks:* in all three cases the data is the caller's own, so no other Account's data is disclosed and NFR-1 is not breached directly. The risk is the one AD-24 was written to prevent: an implementer who needs a read AD-24 does not authorise "disabl[es] RLS, open[s] a second connection, or invent[s] its own bypass — and that bypass then spread[s]." Silence here is what produces the bypass. *Fix:* decide each explicitly rather than leaving it to the slice. Owned-Space names for FR-3 and the Spaces-per-Account count are both legitimately Account-scoped and should be named as permitted reads in AD-24 (own Role, own count, never another Account's) — an amendment AD-24 already anticipates needing. The Token→Role display should be dropped: it is genuinely a Membership read across a boundary, it is decoration rather than function, and UJ-7's point survives without it.
- **[low]** IA line 34 lets the offer indicator read as Account-scoped. *What leaks:* nothing, but the composition is available: the context bar row says it "carries a pending Ownership Offer indicator" and the same table's first column says the bar is "Always present once authenticated" — read together, "always present" plus "carries the offer" implies an offer indicator that follows the Account. Component Patterns line 127 disambiguates correctly ("in the active Space"), so this is a wording risk only. *Fix:* add "for the active Space" to the IA row so the constraint is local to every statement of it.

## 4. Presence and avatars

**Verdict: the avatar and tombstone specs are correct; the identity *label* is the gap, and it is a §6.1 gap rather than an NFR-1 one.** The deleted-Account tombstone is specified well — same shape, muted, **no initials** (DESIGN.md line 361) — which is the right call, since FR-3 wants attribution preserved without the identity persisting.

- **[high]** Neither spine states that an email address may appear only on Owner/Admin surfaces of a Space the Account is a Member of (§6.1, AD-23 final clause). *Locations:* the Assignee picker (line 131), the Presence indicator (line 130), the Avatar row (line 140), Space settings, the Invitation view's "who issued it" (line 135, and see 8.1), and the not-specified "you are signed in as the wrong Account" confirmation (8.4). *What leaks:* an email address to a Member or Viewer, who is not entitled to it. The mechanism is mundane and near-certain: 20px monospace initials and a display name do not disambiguate two people, and the field every implementer reaches for to disambiguate a Membership picker is the email address. §6.1 and AD-23 confine addresses to Owners and Admins; EXPERIENCE.md never mentions the rule at all, and the word "email" appears in it only as an Invitation input and in `Email or password is incorrect.` *Fix:* add a one-line hard rule — no surface outside Space settings' Membership management renders an email address; every other surface identifies a Membership by display name and initials only. Then state what disambiguates two identical display names, because something must: a Membership-scoped discriminator, never the address.
- **[low]** How a display name is resolved for a Membership that no longer exists is unspecified. *What leaks:* thin, and recorded rather than pressed. FR-14 keeps a removed Account's authored description changes in the Space (AD-13's log is append-only), so their attribution keeps rendering to remaining Members — correctly, they were entitled. But if the client resolves the *current* display name by looking the Account up globally rather than reading the name captured on the Membership row, a name change made by that Account after removal propagates into a Space it no longer shares with the viewer. That is a live read of Account state by people with no shared Membership. *Fix:* attribution renders the name captured at authoring time or on the Membership row, never a live global Account lookup.
- **[cleared]** The Assignee picker offering the full Space roster to a Viewer is upstream-sanctioned, not a defect: FR-21 permits assigning a Viewer, FR-30 offers "only Memberships of the active Space" with no Role restriction, and FR-32 shows Presence to every Role. §7 restricts Membership *management* to Owner/Admin, not the visibility of who is in the Space.

## 5. Prefetch, caching and optimistic UI

**Verdict: the weakest area, and the one containing the single most serious finding.** The prefetch rule is good — *"Nothing is prefetched across a Space boundary. A speculative fetch that 404s is still an authorisation refusal and is recorded as one (AD-20). Do not warm caches by guessing."* — and the "route back never to a remembered last-Space" rule shows the author was already thinking about stale client state. But "switching Space carries nothing over" is stated **once**, in prose, in a section about Role legibility, and enumerates only four *presentation* items (Role, filter, scroll position, open Task). It places no obligation on the client's data layer, which is where AD-11 puts a full replica of Space content.

- **[critical]** The local replica's lifetime is never specified, so Space content survives every boundary event by default (EXPERIENCE.md `Foundation` line 25 / AD-11, against `Space Context and Role Legibility` line 65). *What leaks:* Tasks, titles, description text and Presence state for a Space the Account no longer holds a Membership in, rendered on their own screen — or, on a shared browser profile, rendered to a different Account entirely. The mechanism is the default behaviour of every implementation of AD-11, not an exotic mistake. A Blazor WASM client holding a CRDT replica keeps it in memory across a client-side route change so that switching back is instant; and FR-33's five-minute reconnect window plus the *specified* state `Disconnected. Your changes are held locally.` (line 152) pushes it further, toward durable browser storage of unsynchronised text. Then: (i) the user switches to Space B while a live replica of Space A remains resident; (ii) their Membership in A is removed, AD-9 invalidates the lease, the client holds A's content and nothing tells it to drop it; (iii) they switch back to A and the client renders the cached Board **optimistically, before the 404 lands** — a Board for a Space they have no Membership in. Worse, AD-7 forbids only *credentials* in `localStorage`/`sessionStorage`; nothing in either document forbids Space **content** there, so on a shared machine A's Task text survives sign-out and is available to the next Account to sign in. Note the compounding factor: SM-1's isolation suite runs request-level cases against the browser and API surfaces (AD-4), so a purely client-side render of cached content would not fail it. This is the finding most likely to become a verified cross-Space disclosure in a shipped build precisely because the gate cannot see it. *Fix:* promote line 65 from a prose aside to a named, testable lifecycle rule with an explicit trigger set — **Space switch, sign-out, Account switch, lease invalidation (`MembershipChanged`), and back/forward navigation each purge every replica, projection, cached Board, queued frame and pending announcement for the departed Space, synchronously, before any render.** State that Space content is never written to `localStorage` or `sessionStorage` (extending AD-7 from credentials to content), and that any durable buffer FR-33 requires is scoped to one Space, keyed to the session, and destroyed by the same triggers. Then add a client-state case to the isolation suite, because the current suite shape cannot reach this.
- **[high]** Browser-owned surfaces carry Space names outside the app's control, and neither spine mentions any of them. *Locations and mechanisms:* (i) State Patterns line 166, `Delete Space` — *"Require typing the Space name"* feeds Space names into the browser's form-autofill store, which is origin-scoped and Account-agnostic, so the next Account on that profile is offered another Account's Space name as a suggestion in the same dialog; (ii) `document.title` is never specified, and an SPA that sets `Northwind Redesign — Board` writes Space names into browser history, the OS window title, screen shares, and cross-device synced history, where they persist long after the Membership is removed; (iii) the Invitation view is an unauthenticated page that renders a Space name (line 135), so any `<title>` or `og:` metadata on it is scraped into third-party link-preview services — Slack, Teams, WhatsApp — the moment the link is pasted, putting the Space name into chat logs of people with no Membership; (iv) back/forward cache and scroll restoration are browser-owned and keyed to the URL, so they can re-present a previous Space's DOM independently of the app's "carries nothing over" rule. *What leaks:* Space names — identity, not contents — to Accounts and third parties with no Membership. §6.1 makes the enumeration of another Account's Spaces the specific thing nobody may do, "including a Space's Owner", so an autofill dropdown offering them is squarely in scope. *Fix:* `autocomplete="off"` and a non-reusable, non-guessable field name on the delete-Space confirmation input and on every Space, Project and Task name field; a fixed `document.title` of `Yello` with no Space, Project or Task name in it; no Space name in the Invitation view's `<title>` or any `og:`/`twitter:` metadata, and the acceptance route marked `noindex`; explicit disabling of browser scroll restoration on Space-scoped routes.
- **[medium]** Nothing forbids the client from issuing a Space-scoped request for a Space id it has not just been told it belongs to. *What leaks:* no data — this degrades the detection mechanism the release gate depends on. The prefetch rule forbids warming caches *across* a boundary but leaves warm-start prefetching of a remembered last-Space open, and the Cold load row invites exactly that optimisation. Every such prefetch for a Space the Account has since left produces a boundary 404 and, per AD-20, an `AccessRefusal` row classified `CrossSpace`. NFR-7 exists so that "cross-Space access attempts are distinguishable in that record from within-Space permission failures — the two mean very different things"; a client that routinely manufactures `CrossSpace` refusals for its own ordinary users buries a real probing attack in its own noise. *Fix:* state the invariant the "route back" rule already half-implies — **the client never issues a Space-scoped request for a Space id absent from the current switcher response.** It is cheap, mechanically checkable, and it closes the warm-start hole and the deep-link-after-removal hole with one rule.
- **[low]** Browser spellcheck and cloud IME egress of description text is unaddressed. *What leaks:* Task description content to a third party, honestly outside NFR-1's Space-to-Space framing but inside §6.1's spirit and NFR-6's "no content in any log". Several browsers' enhanced spellcheck and several mobile IMEs transmit typed text to a remote service; the description editor is the product's largest free-text surface. *Fix:* a decision either way, recorded — most likely `spellcheck="false"` on the description editor is the wrong trade for usability, so the honest answer is to state that this egress is accepted and note it against §6.4's data-protection gate, where it becomes a real obligation the moment a second data subject exists.

## 6. The 5,000-Task Board and column counts

**Verdict: every count in the spec is intra-Project or intra-Space, with one exception.** The column count's "true total, not the loaded count" is scoped to one Status within one Project within one Space — not an aggregate that crosses anything, and the reasoning given (a count that tracks virtualisation is a lie) is correct. The List View empty state even reasons the point out loud: *"no count of what was excluded, since a count across a filter is still only this Project."* `Moving 4,812 Tasks.` is one Status in one Project moving to another Project in the same Space (FR-41). The Delete Project and Delete Space confirmations state Task and Project counts within the object being destroyed, to the Owner destroying it.

- **[high — same finding as 3.1(ii), recorded here for the count audit]** The *Spaces per Account* bound is the one count in the spec that spans Spaces. State Patterns line 172 generalises `Scale bound reached` to "Any creation surface" with the copy pattern *"This Space has 100 Memberships, the maximum."* Applied to Space creation, the equivalent string is "You have 50 Spaces, the maximum" — an Account-scoped aggregate across Spaces, rendered on a surface AD-24 does not enumerate. See 3.1 for the mechanism and fix.
- **[cleared]** No other count in either spine aggregates across a Space boundary. Presence counts participants on one Task; the column count counts one Status; the bulk-move bar counts one Status's Tasks; the destructive confirmations count within the object deleted. DESIGN.md's `column-count` component is the only pill in the product and carries no other data.

## 7. §6.1's no-analytics rule and the ban on cross-Space aggregate surfaces

**Verdict: correctly handled. Nothing in either spine requires a cross-Space aggregate to render, and the spines actively refuse several places one would be tempting.** IA line 45 is emphatic — *"There is no global home, no cross-Space inbox, no notification centre and no 'all my Tasks' view. §8 does not defer these — it rules them out"* — and `Inspiration & Anti-patterns` repeats it against the reference product. No metrics view, no admin analytics, no dashboard is proposed anywhere. The banned-patterns list rules out badges and counts-as-nudges, which is the vector by which engagement features normally smuggle in an aggregate. AD-20's refusal records, which would make a natural "access log" surface and would be a cross-Space aggregate if built, are correctly never surfaced to a user.

- **[cleared]** `Belonging to no Space` (line 156) needs only the switcher's own list to be empty — a read AD-24 explicitly authorises, not a cross-Space count.
- **[cleared]** The Account settings API Token list needs Space identity per Token, which AD-24 permits as id and name. Only the Role display invites more (3.1(iii)).
- **[cleared]** §10's behavioural measures are correctly absent from both spines. They are operator queries against the datastore, not product surfaces, and neither document proposes rendering one.

## 8. The Invitation and Ownership Offer flows

**Verdict: the in-product surfaces are correct; the flow's two *outbound* artefacts — the offer email and the unauthenticated view's metadata — are where the disclosure surface actually is.** The Invitation view discloses exactly what FR-39 authorises the email to disclose (Space, Role, issuer) and nothing more; the revoked state's copy is exactly right; AD-28's side-effect-free read is honoured, with acceptance as a separate explicit act in both UJ-3 and the Component Patterns row; and the recipient-side offer dialog discloses only facts about the recipient's own future obligations, nothing about the Space they cannot already see as a Member. The Owner-side view names the recipient, whom the Owner can already see in Space settings.

- **[high]** The Ownership Offer email — the one genuinely new outbound artefact in the product — ships with no disclosure constraint anywhere (EXPERIENCE.md UJ-8 step 2 and the upstream-dependency note at line 392; `.memlog.md` entry 29). *What leaks:* potentially Space contents, member counts, or the identity of other Memberships, pushed to an email address and therefore outside the authorisation model entirely once sent. NFR-1 explicitly binds notifications. Compare UJ-2 step 3, which does this correctly for the Invitation: *"naming the Space, the Role, and who issued it — and nothing about the Space's contents (FR-39)."* The offer email has no such clause in either spine, and — because the PRD amendment is owed rather than made — no FR governs it either, so §4.11 has no constraint for it to inherit. An implementer writing "You've been offered ownership of Northwind Redesign (12 Projects, 340 Tasks, 8 Members)" would be adding helpful context with nothing telling them not to. There is a second-order case: AD-5 lapses the offer when the recipient's Membership is removed, but an email already sent cannot be recalled, so anything it carries outlives the Membership that justified it. *Fix:* give the offer email the same explicit clause as the Invitation email — names the Space, the Role change offered, who offered it, and nothing about the Space's contents, its other Memberships, or any other Space — and carry it into the owed PRD amendment as a consequence of the new FR, not just as a notification trigger.
- **[medium]** The Invitation view is an unauthenticated page that renders a Space name, and its page metadata is unspecified. *What leaks:* a Space name into third-party link-preview services and search indexes. See 5.2(iii) for the mechanism; recorded here because this is the surface it lands on and because the Space name on this page is upstream-sanctioned (FR-11 requires the Space and Role be shown before acceptance) — so the leak is not the page, it is everything the page emits *around* the page. *Fix:* no Space name in `<title>` or any `og:`/`twitter:` metadata; `noindex`; no Space name or id in the URL beyond the opaque token.
- **[medium]** There is no state for an unrecognised or forged Invitation token, only for a revoked one (State Patterns line 163). *What leaks:* Invitation existence, on an unauthenticated surface. `This invitation is no longer valid.` is specified for revoked; an implementer will render something else — a generic 404, `Not available.`, or "Invalid link" — for a token that never existed, and any difference makes the acceptance route an existence oracle. Guid entropy makes this impractical to exploit, which is why it is medium rather than high, but it is the same uniformity discipline AD-23 imposes on registration applied one surface over, and it is nearly free. *Fix:* one row covering revoked, accepted, lapsed, expired and unrecognised with a single response — identical words, identical shape, identical duration, per AD-23's own standard.
- **[medium]** The "signed in as the wrong Account" case is unspecified, and it is a common real flow (EXPERIENCE.md line 135 and UJ-3 step 3 cover only the no-Account and correct-Account paths). *What leaks:* an email address to someone not entitled to it. AD-28 requires acceptance to be "authorised on the authenticated Account matching the address the Invitation names", so the client must handle the mismatch — and the helpful implementation is "This invitation is for nadia@example.com; you are signed in as ravi@example.com", which discloses the invited address to whoever holds the link. On a forwarded link that is a stranger. *Fix:* add the row. Refuse without echoing the invited address: state that the Invitation is addressed to a different Account and offer sign-out, naming neither address.
- **[low]** The recipient-side offer dialog will in practice name the current Owner, whose Role a Member has no authorised surface for. *What leaks:* within-Space only, and self-evident from the offer itself — accepting ownership implies someone currently holds it. Recorded because §7 scopes the Membership list to Owner and Admin, so "Ravi is offering you ownership" is technically a Role disclosure to a Member. *Fix:* none needed; noted so a later reader does not mistake it for an oversight.

## Correctly handled — cleared
