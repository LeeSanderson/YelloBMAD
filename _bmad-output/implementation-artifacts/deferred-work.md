It is stable under attack, because rehash fires only on the success path — an attacker probing with wrong passwords never upgrades the row, so the oracle does not decay. The field's own remarks argue this design is the leak-proof one on the grounds that a baked-in constant "would silently stop matching the real path the moment `PasswordWorkFactor` moved"; it creates exactly that leak, in the opposite direction.

  **Why the obvious fix does not exist.** "Bring every row up to the new count" requires the plaintext password, and PBKDF2 is one-way. Heterogeneous verification cost during the migration window is therefore unavoidable, and the window closes only as each Account signs in. This is the same constraint that made the password-normalisation finding a now-or-never decision, and it is worth stating here because it is the thing that makes the cheap options cheap and the real options expensive.

  **The two real remedies, for whoever picks this up.** *A fixed-cost verification budget* — pad every verification to a constant at or above the highest supported count, so the stored count stops being observable. Closes it permanently and immediately; costs worst-case CPU on every sign-in forever, and the padding mechanism has to be written carefully or it becomes the new timing signal. *A layered rehash* — store `PBKDF2_new(PBKDF2_old(pw))`, which upgrades every row eagerly with no plaintext and restores the invariant the current design assumes. Closes it permanently and keeps sign-in cost uniform; changes the stored hash format and how `Verify` reads it, so it is an AD-1 architecture decision with its own migration rather than a patch.

  **What was patched instead.** A duration case that plants a legacy-factor row and measures it against the null arm. It fails today, deliberately: it demonstrates an asymmetry that is already real in the code rather than guarding a property that currently holds. `RehashIntegrationTests:61` already constructs such a row via `HasherAt(FrameworkDefaultIterationCount)` — the arrangement existed, no duration test ever used it, which is why the P0 duration suite stayed green through a defect it was written to catch.
