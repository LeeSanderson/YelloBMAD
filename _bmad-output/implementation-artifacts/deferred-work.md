## Deferred from: code review of 1-4-authenticate-and-hold-a-session-across-every-space (2026-09-19)

- **The remedy for the work-factor timing oracle — a fixed-cost verification budget, or a layered rehash** — `Yello.Infrastructure/Identity/IdentityPasswordHasher.cs:73-75,88`, `PasswordWorkFactor.cs:97-98`. Severity: high when it becomes live. Owner: **whoever raises `PasswordWorkFactor.ChosenIterationCount`, before they raise it.** *Deferred by Lee at code review on 2026-09-19, with the demonstration test patched in now: no stored row is at a legacy count today, so nothing leaks until the factor is raised; the test makes that raise impossible to perform silently, and the remedy is chosen then against the actual cost of each option.*

  **The defect.** PBKDF2's cost follows the iteration count embedded in the *stored* hash. The dummy hash that gives an unknown address something to verify against is minted by the same hasher at the *configured* count. The two are equal only while every stored hash is already current — which is precisely the condition the rehash path exists to violate. Raise the factor from 220,000 to 400,000 and a known address with a pre-raise row costs 220,000 iterations while an unknown address costs 400,000: **a known address answers measurably faster**, which is AD-23/AC4 inverted. It is stable under attack, because rehash fires only on the success path — an attacker probing with wrong passwords never upgrades the row, so the oracle does not decay. The field's own remarks argue this design is the leak-proof one on the grounds that a baked-in constant "would silently stop matching the real path the moment `PasswordWorkFactor` moved"; it creates exactly that leak, in the opposite direction.

  **Why the obvious fix does not exist.** "Bring every row up to the new count" requires the plaintext password, and PBKDF2 is one-way. Heterogeneous verification cost during the migration window is therefore unavoidable, and the window closes only as each Account signs in. This is the same constraint that made the password-normalisation finding a now-or-never decision, and it is worth stating here because it is the thing that makes the cheap options cheap and the real options expensive.

  **The two real remedies, for whoever picks this up.** *A fixed-cost verification budget* — pad every verification to a constant at or above the highest supported count, so the stored count stops being observable. Closes it permanently and immediately; costs worst-case CPU on every sign-in forever, and the padding mechanism has to be written carefully or it becomes the new timing signal. *A layered rehash* — store `PBKDF2_new(PBKDF2_old(pw))`, which upgrades every row eagerly with no plaintext and restores the invariant the current design assumes.
